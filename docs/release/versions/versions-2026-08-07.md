### Проверка размера и полноты состава (перепроверено 2026-08-07)

**Короткий ответ на «136KB — это фактический размер пакета?»: нет.**
136KB — это sdist (исходный архив-рецепт для сборки, не то, что ставит
`pip`). Реальных чисел минимум пять, и они отличаются на два порядка —
см. таблицу выше (`sdist` → `wheel` → `wheel распакован` → `pip install`
с зависимостями сжато → `pip install` на диске). Для «сколько места
займёт у пользователя» релевантны последние две строки, не sdist.

Полнота wheel проверена вживую, не по документации: пересобран
`refigure-0.1.0-py3-none-any.whl`, распакован, каждый из 23 файлов
сверен построчно с реальным деревом `refigure/` в репозитории.
Результат — **точное совпадение, ничего не пропущено и ничего лишнего**:
все 16 исходных `.py`-модулей (`__init__`, `__main__`, `_io`, `api`,
`cli`, `docx_groups` — намеренно плоский, см. `project_extras_isolation_bug`
— плюс `core/`, `docx/`, `vlm/`, `xlsx/` подпакеты целиком), `py.typed`
(PEP 561 маркер типизации — присутствует и запакован), плюс 6
стандартных `dist-info`-файлов (`METADATA`, `WHEEL`, `entry_points.txt`,
`licenses/LICENSE`, `licenses/NOTICE`, `RECORD`). Устаревшие `__pycache__`
в рабочей копии (следы дореформенных плоских модулей `docx.py`/`xlsx.py`/
`vlm.py` до реорганизации на `core`/`docx`/`xlsx`/`vlm` подпакеты) в
архив не попадают — билд-бэкенд их корректно исключает.

Все цифры выше — не оценка, а прямое измерение: `python -m build` +
`unzip -l`/`tar -tzf` для sdist/wheel, реальный `pip install` в 6 чистых
venv (bare/docx/xlsx/docx+xlsx/vlm/vlm-direct) с `du -sb site-packages`
для дискового следа, и `pip install --dry-run --report` (резолвит полное
дерево зависимостей без реальной загрузки) + HEAD-запросы к
`files.pythonhosted.org` за точным сжатым размером каждого файла — для
загрузочного веса.

### Сравнение с похожими конвертерами (2026-08-07)

Та же методология (`pip install --dry-run --report` + HEAD-запросы за
точным сжатым размером, без реальной многогигабайтной загрузки),
применена к Docling и 4 сопоставимым `*→Markdown`-конвертерам —
`unstructured[all-docs]` и `markitdown[all]` (их «полные» extras, для
честного сравнения с фиче-охватом refigure), `marker-pdf`/`pymupdf4llm`
(доп. extras не меняют картину, не задавались):

| Проект | Свой wheel (сжат) | Полная установка (сжатая загрузка) | Пакетов в дереве | Архитектура |
|---|---|---|---|---|
| **`refigure[docx,xlsx]`** | 78KB | **5.6MB** | 11 | чистый XML-парсинг (lxml), без ML |
| `pymupdf4llm` | 172KB | 103.3MB | 12 | PyMuPDF + ONNX-раннер для layout |
| `markitdown[all]` | 69KB | 122.7MB | 49 | смешанная, часть форматов через OCR/onnxruntime |
| `unstructured[all-docs]` | 1.5MB | **3026.6MB (≈3.0GB)** | 152 | spaCy + torch + full NVIDIA CUDA-стек по умолчанию |
| `marker-pdf` | 191KB | **2768.7MB (≈2.7GB)** | 100 | surya-ocr + torch + transformers + CUDA-стек |
| `docling` | 5KB* | **2835.0MB (≈2.8GB)** | 120 | docling-ibm-models + torch + transformers + CUDA-стек |

\* `docling`'s собственный wheel — тонкая API-обвязка; реальный код и
ML-модели живут в отдельно устанавливаемых `docling-core`/
`docling-ibm-models`/`docling-parse` — иллюстрация того, почему «свой
wheel» без учёта дерева зависимостей — вводящая в заблуждение метрика
сама по себе, ровно то, из-за чего наша собственная таблица выше не
останавливается на 78KB.

**Вывод, количественно подтверждающий позиционирование проекта**
(`CLAUDE.md`: «native OOXML chart-data extraction... no rasterize/OCR/
VLM»): три из четырёх конкурентов по умолчанию тянут полный GPU-стек
PyTorch + NVIDIA CUDA (~2.7–3.0GB каждый) для задачи, которую refigure
решает прямым разбором XML внутри OOXML-контейнера — 5.6MB, в
**~500 раз** меньше. `pymupdf4llm`/`markitdown` заметно легче
докling-класса, но всё равно на два порядка тяжелее — оба используют
onnxruntime под капотом хотя бы для части форматов, а refigure — нет ни
для одного.


PyPI. PyPI не позволяет переиспользовать номер версии даже после `yank` —
делать осознанно, не как побочный эффект чего-то другого.
