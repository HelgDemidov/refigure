## 1. SAST — ruff `S`-ruleset, НЕ отдельный Bandit

**Корректировка исходного плана**: в roadmap-записи 7b и в постановке
этой задачи значился Bandit. Живая проверка отменяет это решение —
`refigure/vlm/client.py:79` уже несёт `# noqa: S310` (унаследовано из
исходного пайплайна) — сигнал, что кодовая база уже когда-то писалась с
оглядкой на flake8-bandit-style правила. Проверил: ruff (уже
установлен, уже в `quality`-джобе) содержит СОБСТВЕННУЮ реализацию
flake8-bandit — категория правил `S`. Живой прогон
`ruff check --select S refigure/` даёт **ровно 3 находки**, все в
`refigure/vlm/`:

- `S603`/`S607` (`vlm/__init__.py:508-509`) — `subprocess.run(["soffice",
  ...])`: непроверяемый untrusted-input призыв + частичный (не
  абсолютный) путь к исполняемому файлу.
- `S310` (`vlm/client.py:74`) — `urllib.request.Request(...)`: URL-схема
  не проверяется. Существующий `# noqa: S310` стоит на строке 79
  (`urlopen(...)`), а ruff относит нарушение к строке 74 (`Request(...)`)
  — **эта noqa ничего не подавляла бы**, включи мы `S` без проверки (не
  протестирован раньше — категория не была включена вообще).

Все три — легитимные, уже обоснованные паттерны (soffice-рендер,
фиксированный HTTPS-эндпоинт `OPENROUTER_CHAT_URL`), не баги. План:
- `pyproject.toml`: `select = ["E", "F", "I", "S"]`;
  `per-file-ignores` — `"tests/**" = ["S"]`, `"scripts/**" = ["S"]`
  (проверено: 706 находок в `tests/` — почти все `S101`, bare `assert`
  внутри pytest-тестов, ожидаемый и бессмысленный шум там; тот же
  принцип, что уже применён к mypy — `--strict` только на `refigure/`).
  С этими исключениями `ruff check refigure tests scripts` даёт те же
  ровно 3 находки, проверено вживую.
- `S607` — **реальный фикс**, не noqa: резолвить `soffice` в абсолютный
  путь через уже существующий `shutil.which("soffice")` (используется в
  `_soffice_available()`, но не передаётся в сам `subprocess.run`) — не
  просто глушит правило, а закрывает PATH-hijacking класс риска.
- `S603` — обоснованный `# noqa: S603` с комментарием (это и есть
  назначение вызова, пути — из `tempfile.TemporaryDirectory()`/
  локально записанного файла, не пользовательский ввод).
- `S310` — noqa переносится на фактически нарушающую строку (`Request(`,
  74), не `urlopen` (79).
- Bandit как отдельный инструмент — **не берём**: нулевой новый
  зависимость/CI-шаг против ruff-`S` (уже установлен, уже в CI) при том
  же практическом покрытии для этого размера кодовой базы — тот же
  принцип «не дублировать», что уже применён к OSV-Scanner/Phylum.

## 2. Secret-scanning — Trivy, закреплён по SHA, не по тегу

Узкая роль (только `scanners: secret`, не замена SCA) не изменилась.
**Новая находка, меняющая КАК подключать**: `aquasecurity/trivy-action`
пережил реальный supply-chain-компромисс 19-20 марта 2026 — похищение
credentials из GitHub Actions runner, все теги `0.0.1`-`0.34.2`
скомпрометированы (~12 часов экспозиции), плюс сам `trivy` CLI
(`v0.69.4`-`0.69.6`) и `setup-trivy` (все релизы кроме `v0.2.6`). Тот
же класс риска, за который уже отвергнут LiteLLM (`CLAUDE.md`) — тег
`@v0.36.0` (текущий стабильный, после инцидента) недостаточен сам по
себе для максимальной защиты; официальная рекомендация после инцидента
— закрепление по commit SHA, не по тегу (теги можно физически
переуказать). Проверено вживую (`git ls-remote --tags`): `v0.36.0` →
коммит `ed142fd0673e97e23eac54620cfb913e5ce36c25`.

- `.github/workflows/ci.yml`, `quality`-джоб, новый шаг после
  `pip-audit`:
  ```yaml
  - name: Trivy secret scan
    uses: aquasecurity/trivy-action@ed142fd0673e97e23eac54620cfb913e5ce36c25  # v0.36.0
    with:
      scan-type: fs
      scanners: secret
      exit-code: "1"
  ```
- Живая проверка (`grep` по `refigure`/`tests`/`vlm`) не нашла ничего
  похожего на реальный секрет — но это не замена настоящему прогону;
  первый живой запуск (после восстановления Actions) может дать
  false positive на тестовые fixture-строки, триаж по факту через
  `.trivyignore`, не заранее вслепую.

## 4. Socket — отклонён (2026-08-07)

**Не взят, живое основание, не «не автоматизируется»**: попытка
установки вскрыла реальное ограничение — Socket-приложение не
предлагает установку на личный аккаунт, только на организацию. Репозиторий
принадлежит личному `HelgDemidov`, не организации; GitHub App,
установленный на уровне организации, видит только репозитории ЭТОЙ
организации — реальное покрытие `refigure` потребовало бы переноса
репозитория в новую организацию (смена URL, правка README-бейджа/
`CLAUDE.md`/`pyproject.toml`-ссылок/git remote/branch protection).
Пользователь решил: цена (перенос репозитория) не оправдана для
одного дополнительного инструмента, когда typosquatting/supply-chain
уже частично покрыт связкой pip-audit (SCA) + CodeQL + ruff-`S` + Trivy.
Не откладывается на будущее как «сделать после» — явный отказ.

## 5. Аудит — план

**После**, не параллельно с §1-4 — эффективнее, когда есть на что
опереться/что триажить (первые реальные Bandit-класса/CodeQL/Trivy
результаты, ждут восстановления GitHub Actions). Скоуп — `refigure/`:
- Untrusted-input поверхности: `zipsafe.py` (уже есть прецедент —
  `feedback_untrusted_input_handling` memory), XML-парсинг (`lxml`
  везде, уже проверено), VLM prompt-injection (документ-контент
  попадает в промпт-шаблон `FIG_PROMPT`).
- Pluggable-injection поверхности: `VlmClient`/`VlmCacheBackend`
  Protocol — их не покрыть автоинструментом (произвольная реализация
  извне), только ручным разбором контракта.
- CLI: path handling в batch-режиме (`_plan_batch`/`_resolve_batch_
  sources`) — traversal-класс риска.
- Credential handling: `vlm_api_key`/провайдерные ключи — не логируются
  ли где-то по ошибке.
- Метод — тот же adversarial-verify, что уже применён в проекте
  (witness-gate/`judge_defects` panel-редизайн): находка не
  принимается без независимого скептического прохода. Ролевые проходы
  (input-validation/injection-surface/credential-handling), не один
  общий grep.
- **Agent-фан-аут во время самого аудита требует явного разрешения
  пользователя в момент выполнения** (`CLAUDE.md` §Do NOT) — этот спек
  его не предполагает заранее выданным.
- Находки: мелкие/уверенные — фикс-коммиты в этом же PR; крупные/
  неуверенные — фиксируются отдельно (issue/новый спек), не
  форсируются в этот PR ради закрытия чек-листа.

## Пересчёт трудоёмкости (roadmap)

Roadmap держит ~11% предварительно для security-половины 7b. Живая
проверка §1 (Bandit → ruff-`S`, найдено и обосновано ровно 3 находки,

непредсказуем заранее. Итог: оценка подтверждается, материально не
меняется — `execution-sequence-2026-08-04.md` не требует правки.

## Тестовое покрытие

Статический-анализ-конфиг, не рантайм-поведение — новых pytest-тестов
не требует (та же логика, что `ruff`/`mypy`/`pip-audit` в `quality`-джобе
и так не покрыты unit-тестами). Верификация — сам факт, что
`ruff check refigure tests scripts` проходит чисто, и что Trivy-шаг
реально выполняется (после восстановления Actions). Фиксы по итогам
аудита (§5) получают тесты по обычной практике — состав определится по
факту находок, не здесь.
