# Оценка целесообразности: стоит ли извлекать конвертеры исходного пайплайна в refigure

Дата: 2026-08-04. Источник конвертеров — рабочий приватный пайплайн (его
`convert/`-подпакет), не сам refigure (в нём кода ещё нет).

## Протокол исследования (кратко)

4 независимых агента, запущены параллельно:
- 3 агента — построчный код-ревью одного конвертера каждый (PDF / DOCX / XLSX + общий
  chart-движок `chart_data.py`/`chart_render.py`, используемый и DOCX, и XLSX). Задача:
  скептически проверить заявления `CLAUDE.md` против реального кода, оценить связанность
  с остальным пайплайном (что нужно для автономной экстракции), реальную глубину тестов,
  прогнать тесты лично, а не поверить на слово.
- 1 агент — рыночное исследование (WebSearch/GitHub-поиск): текущий (середина 2026)
  ландшафт PDF/DOCX/XLSX→Markdown инструментов, отдельно — есть ли где-то уже связка
  «нативное чтение OOXML-данных чарта + настоящая mermaid-диаграмма с рендер-валидацией»
  и «позиционные zero-loss маркеры для составных фигур независимо от VLM».

Каждый агент отчитывался конкретными указаниями на файл/строку/тест, без общих слов.
Синтез (этот документ) — ручной, мой собственный, не копипаста агентских отчётов.

## Выводы (подробно)

### PDF-конвертер — не флагман

`pdf_to_markdown.py`+`pdf_graphics.py` (~1170 строк) — честно декуплены от пайплайна
(ноль импортов из `core/`), тесты реальные (Hypothesis-property-тесты на инварианты типа
«колонки никогда не режут слово пополам», регрессии, привязанные к конкретным живым
багам). Но сама техника — projection-profile для колонок, кластеризация по размеру
шрифта для заголовков, векторная геометрия для графиков — это то, что построит любой
толковый инженер с `pdfplumber` за пару дней. Калибровка — на 2-3 реальных документах
(Сингапур, Эстония). Собственный вердикт ревьюера: «не отличается от того, что построил
бы компетентный инженер».

Рынок это подтверждает: **208 репозиториев** с тегом `pdf-to-markdown` на GitHub,
включая MarkItDown (Microsoft, 171k★), Docling (IBM, 64k★), marker (38k★, отдельный
стартап Datalab), MinerU (76k★), LlamaParse, Reducto ($108M инвестиций). Выходить в этот
сегмент с обычным PDF-конвертером — почти нулевой шанс на внимание.

### DOCX + XLSX + общий chart-движок — вот что реально ценно

Три независимых источника (два кодовых ревью + рыночный агент) сошлись на одном:

- **`chart_data.py`/`chart_render.py`** реально читают `numCache`/`strCache` напрямую из
  OOXML — без рендера, без OCR, без VLM. Подтверждено чтением кода (нет ни одной ссылки
  на `<c:f>` резолюцию формул), не только докстрингами.
- **Mermaid-гейт — настоящий рендер**, не синтаксическая проверка: агент лично прогнал
  91 тест (все зелёные, включая интеграционный тест на реальном датасете World Bank,
  55 чартов, 9 листов) и поймал через этот гейт реальный баг (`pie title "T"` —
  синтаксически валиден, но рендерится с буквальными кавычками — поймала бы только
  рендер-проверка).
- **Позиционные sentinel-маркеры** в `docx_groups.py` гарантируют нулевую потерю позиции
  и подписей ДО любого VLM-прохода — порядок кода это доказывает (подпись извлекается
  ДО выреза объекта), не просто заявлено в докстринге.
- Движок уже сегодня почти автономен: `chart_data.py`/`chart_render.py` — ноль импортов
  из `core`/`schema`/`.env`. Оценка экстракции — «меньше дня работы».

**Рынок — решающее доказательство.** Рыночный агент искал именно эту связку и не нашёл
ни у одного крупного, хорошо профинансированного игрока:
- MarkItDown (Microsoft) — открыто признаёт: «native Excel charts are not extracted».
- Docling (IBM, 64k★) — открытый, **больше года не тронутый** баг #1287: «DOCX to
  Markdown, the emf and chart... are lost».
- LlamaParse/Reducto/MinerU — гоняют изображение чарта через VLM даже когда данные лежат
  готовые в XML открытым текстом.
- Разрозненные хобби-попытки закрыть именно эту нишу существуют, но ни одна не собрала
  полную цепочку: PaddleOCR (только DOCX, HTML-таблица, без Mermaid), `undoc`
  (Rust, 33★, таблица без Mermaid), `office_oxide` (Rust, 88★, вообще не таблица —
  «plain text»).

Сегменты по GitHub-тегам: `docx-to-markdown` — **33 репозитория** (в 6 раз менее забито,
чем PDF), `xlsx-to-markdown` — **4 репозитория** (в 50 раз менее забито).

Это не «изобретение велосипеда» — это единственный из трёх кусков, где велосипеда
объективно ещё нет.

### Пакаджинг-прецедент

Узкие однонаправленные пакеты (marker/Datalab, camelot/tabula/pdfplumber) успевают
взлететь, но только с реальным, проверяемым отличием — не голой узостью самой по себе
(теги `docx-to-markdown`/`xlsx-to-markdown` завалены безуспешными инструментами на
2-150★ без такого отличия).

## Вердикт

**Да, стоит извлекать — но не в текущем позиционировании «PDF+DOCX+XLSX единым
фронтом».** Веди с DOCX+XLSX chart-engine — единственная часть, которая одновременно
(а) реально сложная и проверенная построчным ревью, (б) объективно отсутствует на рынке
даже у игроков с сотнями миллионов инвестиций, с прямым доказательством (открытый
годовалый баг Docling). PDF-конвертер можно публиковать в том же пакете (код не
стыдный, тесты честные) — но не как заявку на конкуренцию с marker/Docling, а как
довесок, с честным описанием ограничений (калибровка на 2-3 документах, ноль поддержки
3-колоночных layout, риск на CJK).

Перед публикацией: калибровочный корпус везде тонкий (PDF — 2-3 документа, DOCX/XLSX —
по факту один реальный файл каждый, пусть и хорошо использованный) — это стоит честно
писать в документации пакета, не продавать как «battle-tested».

## Бонус: стратегия исправления бага mermaidx (найден при код-ревью, исправлен и
верифицирован в этой же сессии)

### Баг

`chart_render.py::mermaid_renders()` — собственный докстринг обещал: «любой отказ,
включая недоступность самой библиотеки → False, fail-safe, вызывающая сторона просто
теряет mermaid-блок, НЕ конвертацию целиком». Но:

```python
def mermaid_renders(code: str) -> bool:
    import mermaidx  # <- ВНЕ try/except
    try:
        mermaidx.render(code).svg()
        return True
    except Exception:
        return False
```

`import mermaidx` стоял **вне** `try`. Реально отсутствующий `mermaidx` падал
необработанным `ModuleNotFoundError` через весь call path
(`render_chart` → `docx_groups`/xlsx-чарт-рендер) — крашил конвертацию целиком, а не
деградировал. В исходном пайплайне сегодня это спит, потому что `mermaidx` — жёсткая зависимость
всего `requirements.txt`. Становится реальным крашем в момент, когда refigure сделает
`mermaidx` опциональным per-format extra (`[docx]`/`[xlsx]`) — ровно план из README
этого репо.

### Процесс (по явному запросу — brainstorming, затем systematic-debugging)

**Brainstorming** (design-диалог с пользователем):
1. Уточняющий вопрос — только документ или ещё патчить сам баг в исходном пайплайне? →
   **патчим и там тоже**, раз источник истины там.
2. Уточняющий вопрос — UX при отсутствии `mermaidx`: тихо или предупредить? →
   **предупредить один раз** (не спамить лог на документ с десятками чартов).
3. Сверка с конвенцией кодовой базы: `figures_vlm.py` везде использует
   `logger.warning(...)` для «деградировал, но продолжил» — не `warnings.warn`. Держусь
   этой конвенции, а не абстрактно-идиоматичного варианта.
4. 3 подхода сравнены: (A) минимальный патч (просто занести импорт под `try`) — не
   выполняет требование «предупредить один раз», отклонён; (B, выбран) module-level
   опциональный импорт + capability-флаг + warn-once через `functools.lru_cache`; (C)
   типизированное исключение — ломает существующую конвенцию «любой сбой → False» без
   реальной пользы, отклонён.

**Systematic-debugging** (воспроизведение + верификация):
1. **Phase 1, эмпирическое воспроизведение** (дважды — на низком уровне `mermaid_renders()`
   напрямую и через реальный публичный вход `render_chart()`, симуляция отсутствия через
   `sys.modules['mermaidx'] = None`): подтверждён `ModuleNotFoundError`, ровно как
   предсказано статическим чтением кода.
2. **TDD, красный→зелёный**: написан новый файл
   `tests/unit/convert/test_chart_render_missing_mermaidx.py` (6 тестов) ДО фикса —
   подтверждено падение (`AttributeError`, фикстура ссылалась на ещё не существующий
   `_warn_missing_mermaidx`), затем реализован фикс, все 6 тестов позеленели.
3. **Регрессия**: полный прогон `tests/unit/convert/` (546 тестов) +
   `test_xlsx_charts_datadriven.py`/`test_docx_groups_live.py` (13 интеграционных) —
   **0 регрессий**, 559/559 зелёных.
4. **Повторное воспроизведение исходного сценария на исправленном коде** — краш
   отсутствует, вывод честно деградирует в подпись+таблицу, warning залогирован.
5. `ruff check`/`ruff format`/`mypy` — чисто.

### Финальный код (реализовано и закоммичено в исходном пайплайне, не запушено)

```python
import logging
from functools import lru_cache

from convert.chart_data import ChartData

logger = logging.getLogger(__name__)

# mermaidx is an optional per-format extra (refigure [docx]/[xlsx]) — a
# pdf/html-only install must not require it.
try:
    import mermaidx
except ImportError:
    mermaidx = None


@lru_cache(maxsize=1)
def _warn_missing_mermaidx() -> None:
    logger.warning(
        "mermaidx not installed — chart diagrams disabled, falling back to "
        "tables only (install refigure[docx]/[xlsx] to enable rendering)"
    )


def mermaid_renders(code: str) -> bool:
    if mermaidx is None:
        _warn_missing_mermaidx()
        return False
    try:
        mermaidx.render(code).svg()
        return True
    except Exception:  # noqa: BLE001
        return False
```

### Что перенести при реальной экстракции в refigure

Этот же паттерн (module-level `try/except ImportError` + capability-флаг + warn-once
через `lru_cache`) стоит переиспользовать как общий рецепт для **любой** будущей
опциональной зависимости пакета, не только `mermaidx` — например, если когда-нибудь
`refigure` добавит VLM-интерпретацию составных фигур (сейчас сознательно вне скоупа
`[pdf]`/`[docx]`/`[xlsx]`), внешние опциональные зависимости того слоя (LibreOffice/
`soffice`, VLM-клиент) должны деградировать по тому же рецепту, не изобретать новый.
