# refigure v1 — скоуп, архитектура пакета, дизайн API (решения зафиксированы 2026-08-04)

Продолжение [`converter-viability-assessment-2026-08-04.md`](../converter-viability-assessment/converter-viability-assessment-2026-08-04.md)
(тот документ — вердикт «стоит ли извлекать» и рыночное обоснование; этот —
как именно). Все решения ниже приняты в диалоге с пользователем в тот же день.

## 1. Скоуп v1

- **PDF-конвертер исключён из проекта полностью** — не «отложен», а не входит в
  видение refigure вообще. Обоснование в assessment-документе: техника не отличается
  от того, что построит любой инженер с `pdfplumber` за пару дней, а сегмент
  PDF→Markdown — самый забитый на рынке (208 репозиториев на теге, включая игроков
  с сотнями миллионов инвестиций).
- **Один общий пакет для DOCX + XLSX**, не два отдельных пакета на формат.
- **VLM-интерпретация составных фигур** — переносится из исходного пайплайна и прорабатывается
  сразу, но **не активна в v1**: готовится как `[vlm]` extra, для будущего
  подключения без архитектурного долга.
- **MCP-сервер — не в v1.** Обозначен как **главная цель v2** (структурно занимает
  место, которое в исходном видении refigure занимал PDF-конвертер).

## 2. Архитектура пакета

**Один пакет `refigure` на PyPI, extras по формату + отдельно по возможности:**
- `refigure[docx]` — DOCX-конвертер (`mammoth`+`markdownify`+`lxml`)
- `refigure[xlsx]` — XLSX-конвертер (`openpyxl`+`lxml`)
- `refigure[vlm]` — облачная интерпретация составных фигур (когда будет реализована)
- `refigure[docx,xlsx]` — оба формата, без VLM
- Голый `pip install refigure` — только core (chart-движок), без работающего
  конвертера ни на один формат; ожидаемое, стандартное поведение для этого паттерна
  extras (аналог `sqlalchemy[postgresql]`), не баг.

**Не два пакета на VLM (`refigure`/`refigure-vlm` или lite/full) — рассмотрено и
отклонено.** Причины:
- Уже противоречит собственному питчу README refigure — там ОДИН продукт
  с опциональным VLM-слоем поверх, не два продукта.
- Два номера версий, два CI, два PyPI-листинга — постоянный, не разовый налог на
  сопровождение.
- Разделение пакетов оправдано для **взаимоисключающих** вариантов
  (`tensorflow-cpu` xor `tensorflow-gpu`), а не для «база + опциональная фича поверх»
  — у refigure ровно второй случай.

**Независимые подмодули по формату** (`refigure/docx.py`, `refigure/xlsx.py`) —
каждый импортирует ТОЛЬКО свою тяжёлую зависимость внутри себя. Так
`pip install refigure[xlsx]; import refigure.xlsx` никогда не трогает `mammoth`,
даже не пытается его импортировать. Это архитектурное решение, не постфактум-патч:
без него пришлось бы городить try/except-обёртку вокруг `mammoth`/`openpyxl` по
образцу сегодняшнего фикса `mermaidx` — а так эта проблема просто не возникает.

**`chart_data.py`/`chart_render.py` — core, всегда устанавливаются.** Лёгкие
(только `lxml`), используются и DOCX-, и XLSX-путём. `mermaidx` внутри
`chart_render.py` остаётся отдельным опциональным слоем — паттерн (module-level
`try/except ImportError` + capability-флаг + `lru_cache`-based warn-once через
`logger.warning`) уже реализован и верифицирован сегодня в исходном
пайплайне, переносится как есть.

**VLM — две независимые оси, не одна:**
1. **Install-time** (`[vlm]` extra) — есть ли способность вообще; без extra —
   тяжёлые зависимости (облачный клиент, вызов LibreOffice/`soffice`) не тянутся.
2. **Runtime-тоггл** (`use_vlm: bool` параметр) — использовать ли VLM на конкретном
   вызове, даже если extra установлен. Нужен отдельно от extra: например, VLM
   установлен, но документ конфиденциальный — тот же принцип, что уже есть в
   исходном пайплайне (`sensitivity`-гейт перед облачным эмбеддингом, `embed.py`).

Без extra или с `use_vlm=False` — честная деградация в позиционный маркер+подпись
(zero-loss floor), не ошибка и не урезанный режим — по рыночному исследованию это
самостоятельно ценный режим, не «недоделанный VLM».

## 3. Публичный API — «взрослый», не голая строка

- **`ConversionResult`-датакласс**, не bare `str`:
  `markdown`, `warnings` (структурные находки — «чарт без numCache, откат к
  caption-only», и т.п.), `charts_found`/`charts_rendered`, `groups_found`,
  `vlm_used`. Прямой аналог уже доказавших ценность сигналов из исходного
  пайплайна (`doc_facets.fidelity`, `chunks.reconstruction`) — конкуренты (MarkItDown и др.)
  отдают голую строку без интроспекции, это реальная точка отличия.
- **Типизированные исключения**: `UnsupportedFormatError`, `CorruptArchiveError`,
  `MissingOptionalDependencyError` (с указанием, какой extra ставить).
- **`strict: bool`** — падать (`True`) или деградировать с записью в `warnings`
  (`False`, по умолчанию), когда запрошенная возможность недоступна.
- **Вход — path ИЛИ bytes/file-like объект**, не только путь на диске (`mammoth`/
  `openpyxl` сами это умеют — не терять на уровне обёртки).
- **Конфиг-объект/клиент**, не россыпь kwargs на каждый вызов — особенно раз у
  VLM-слоя реально есть, что настраивать (модель, таймаут, кэш-бэкенд). Паттерн
  `httpx.Client`/boto3-клиентов.
- **Кэш VLM-ответов — подключаемый бэкенд**, не хардкод sidecar-файла
  (`.figures.yaml` — конвенция самого исходного пайплайна, завязана на его
  layout корпуса; библиотеке нужна гибкость под чужие деплойменты).

### Sync vs async — проверено, не предположено

VLM-HTTP-клиент в исходном пайплайне **полностью синхронный** (`def`, не `async def`) —
проверено чтением файла, не предположено. Портирование даёт sync API бесплатно.

**Async — не для всей библиотеки.** Ядро (`chart_data`/`chart_render`/
`docx_groups`/`xlsx_charts`, `mammoth`, `openpyxl`, парсинг XML, рендер mermaid
через встроенный QuickJS) — на 100% CPU-bound, локальная работа; async не даёт
здесь ничего, только накладные расходы на event loop.

VLM-слой — другое дело: при батч-конвертации корпуса с множеством фигур
последовательные (сегодня) сетевые вызовы к облачной модели можно распараллелить
(`asyncio.Semaphore`, с уважением к рейт-лимитам) — потенциально разница не в
проценты, а в разы для целевого сценария refigure (LLM/RAG-инжест корпусов, не
разовая конвертация одного файла). Но перевод всей библиотеки в async — «заражает»
весь вызывающий код и требует держать две параллельные API-поверхности (как
`OpenAI`/`AsyncOpenAI`) ради выигрыша, применимого только к необязательному слою.

**Решение**: ядро остаётся синхронным. Async, если понадобится — узкая
batch-точка входа именно для VLM (`convert_batch_async(paths, vlm_concurrency=N)`
в духе), решается **когда VLM реально пойдёт в разработку** (после v1, extra),
не блокирует дизайн API v1.

## 4. Roadmap

- **v1**: DOCX + XLSX, chart-engine (нативный numCache + mermaid с рендер-валидацией),
  zero-loss позиционные маркеры для составных фигур. VLM — код портирован и готов,
  но `[vlm]` extra не анонсируется/не продвигается как готовая фича. Без MCP.
  **Статус 2026-08-07: реализовано, готово к релизу** — PR #1-#17 смёржены,
  версия `0.1.0` подготовлена локально (тег `v0.1.0` создан); фактическая
  публикация на PyPI — единственный оставшийся, намеренно ручной шаг (см.
  `docs/release/versions/versions-2026-08-07.md`, `CLAUDE.md` §Status).
- **v1.x**: `[vlm]` extra выходит из подготовки в релиз, вместе с ним решается
  вопрос async batch-точки входа (§3). Не начато.
- **v2**: MCP-сервер — тонкая обёртка над уже «взрослым» API v1 (близко к
  тривиальной инженерии при правильно спроектированном API, см. §3), целится в
  ровно ту аудиторию, под которую уже позиционирован весь проект (агентские
  LLM/RAG-инструменты, теряющие графики при конвертации документов). Открытый
  вопрос на момент реализации — передача файла через MCP: путь на диске (просто
  для локального Claude Code/Desktop, неудобно для удалённых MCP-развёртываний)
  или base64-контент (работает удалённо, раздувает payload на больших docx/xlsx) —
  решать отдельно, не походя, когда до этого дойдёт очередь. Не начато.
