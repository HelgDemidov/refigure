# Дополнение: слепые зоны ведущих PDF-конвертеров в экстракции инфографики

Дата: 2026-08-19. Дополняет `converter-viability-assessment-2026-08-04.md`, не
заменяет — исходный вердикт (PDF вне v1 scope) не меняется, но уточняется и
укрепляется новыми данными. Повод — пользователь усомнился: не ошибка ли исключать
самый распространённый формат-кандидат полностью, и нет ли у топовых PDF-конвертеров
реального, закрываемого пробела именно в инфографике, который стоило бы закрыть
переносом chart-engine refigure на PDF.

## Протокол

3 параллельных агента (запущены через `/brainstorming`, spike-классификация,
разрешение на субагентов получено явно от пользователя — см. `CLAUDE.md` §Do NOT):

- **Агент 1** — структурный потолок формата: есть ли у born-digital PDF (matplotlib/
  Excel/PowerPoint/LibreOffice/Illustrator/ggplot2/Vega-Lite-экспорт) хоть какой-то
  аналог OOXML `<c:numCache>`/`<c:strCache>` — кэшированных значений чарта, читаемых
  без рендера/OCR/VLM.
- **Агент 2** — issue-трекеры 9 ведущих PDF→Markdown/structured-data инструментов
  (Docling, MarkItDown, marker, MinerU, Unstructured, LlamaParse, Reducto,
  PyMuPDF/pymupdf4llm, pdfplumber): задокументированные, датированные проблемы именно
  с чартами/графиками/инфографикой.
- **Агент 3** — prior art по векторному «де-рендерингу» чартов (без OCR/VLM) + как
  лидеры сегодня обращаются с составными инфографиками, которые не могут семантически
  распарсить.

Каждый агент отчитывался конкретными ссылками (issue-номер, дата, цитата мейнтейнера,
пункт спецификации), не общими впечатлениями — тот же протокол, что в исходном
assessment.

## Выводы

### 1. Структурный потолок — техника refigure не переносится на PDF ни при каких усилиях

PDF — формат отображения, не данных. Ни один массовый генератор чартов (matplotlib,
R `cairo_pdf()`/`pdf()`, Excel/PowerPoint/LibreOffice-экспорт, Vega-Lite) не оставляет
в файле ничего похожего на `numCache` — только векторные операторы рисования
(`m`/`l`/`c`/`S`/`f`/`Tj`) без единой связи между path'ом столбика и его подписью.

Проверенные PDF-механизмы, теоретически способные нести структуру (ISO 32000-2):
Tagged-PDF `/Figure`+`Alt`-текст (§14.8, обязателен по PDF/UA) — несёт
человекочитаемое ОПИСАНИЕ, не значения; Optional Content Groups/слои (§8.11) — никто
не мапит серии данных на них; marked-content property lists (§14.6) — теоретически
возможно, реально не используется никем; associated files (§14.13) — единственный
РАБОЧИЙ прецедент того же паттерна («кэш данных рядом с рендером») в природе:
ZUGFeRD/Factur-X встраивает целый XML-инвойс как `AFRelationship=Data` рядом с
PDF/A-3-страницей — но ни один инструмент построения чартов этот механизм не
использует.

Единственное частичное исключение — легаси Graph-объект Illustrator (`Object > Graph
> Data`): при экспорте с «Preserve Illustrator Editing Capabilities» данные
сохраняются в приватном блобе `/PieceInfo` (§14.5). Но это недокументированный
проприетарный формат, читаемый только самим Illustrator — для стороннего конвертера
эквивалентно «недоступно».

Решающее косвенное доказательство: **сам Docling** в 2026-м реализовал «понимание
чартов» для PDF через VLM (`ibm-granite/granite-vision-3.3-2b-chart2csv-preview`,
[блог 2026-02-03](https://docling.ai/blog/20260203_00_chart_understanding_in_docling/)),
тогда как для DOCX/XLSX/PPTX в июле 2026-го (PR
[#3777](https://github.com/docling-project/docling/pull/3777)/
[#3794](https://github.com/docling-project/docling/pull/3794)/
[#3809](https://github.com/docling-project/docling/pull/3809)) сделал то же самое
детерминированно, читая `c:numCache`/`c:strCache` — «no LibreOffice required, fully
deterministic». Один вендор, одна задача, два разных решения — потому что данные
реально по-разному доступны в этих форматах, не потому что для PDF не хватило
усилий.

### 2. Реальные пробелы у 9 инструментов подтверждены — но другой природы, не data-cache

Issue-трекеры (проверено live 2026-08-19) подтверждают: семантическое распознавание
чартов в PDF — незрелая область почти везде, но каждый инструмент проваливается
по-своему:

| Инструмент | Заявлено в доках | Ключевое живое доказательство | Статус |
|---|---|---|---|
| Docling | опциональный `do_chart_extraction` (default `False`), VLM-based | [#2176](https://github.com/docling-project/docling/issues/2176) открыт 11+ мес, только бот-ответ «outside scope» | частично закрыто в 2026, но не для триажа |
| MarkItDown | не заявлено вообще | [#2049](https://github.com/microsoft/markitdown/issues/2049)/[#2055](https://github.com/microsoft/markitdown/issues/2055) — изображения из PDF даже не извлекаются нормально | нет обработки чартов в принципе |
| marker | только generic image, без chart-to-data | [#802](https://github.com/datalab-to/marker/issues/802) — мейнтейнер: «low priority… would be a while», закрыт без фикса | явно депримировано |
| MinerU | собственный техотчёт признаёт: старая версия «discarding potentially valuable information such as chart data» | [#1392](https://github.com/opendatalab/MinerU/issues/1392) открыт 15.5 мес, закрыт после Pro-релиза 2026-04 | единственный реально закрытый случай |
| Unstructured | чарт не выделен как отдельная сущность нигде в доках | по 6 вариантам поиска — ни одного профильного issue | пробел, но не сформулирован даже пользователями |
| LlamaParse | агрессивный маркетинг: «extracts charts… into structured data» | [#272](https://github.com/run-llama/llama_cloud_services/issues/272) открыт **2+ года**, мейнтейнер: «we currently don't support this very well» | самый явный разрыв маркетинга и реальности |
| Reducto | лучший в классе, agentic extract→replot→verify | собственный блог: «5–10% ошибка на точку данных» даже после верификации | недоступно даже топовому игроку целиком |
| PyMuPDF/pymupdf4llm | понятия «чарт» нет в модели данных вообще | [#3690](https://github.com/pymupdf/PyMuPDF/issues/3690) — мейнтейнер закрыл как не-баг, перевёл в Discussions | постоянный признанный не-фикс |
| pdfplumber | не заявлено | ни одного профильного issue по 6 вариантам поиска | тишина = не сформулированная проблема, не решённая |

Вывод: пробел настоящий и широкий, но не data-cache уровня — это семантическое
распознавание значений на изображении/векторе, тот же класс задачи, что VLM/OCR-чарт-
экстракция, а не «прочитать готовое число из файла». Закрыть его «крепким
середнячком» нельзя — даже тот, кто старается больше всех (Reducto), не решил его
полностью, инвестировав ресурсы, несопоставимые с портированием
`pdf_to_markdown.py`/`pdf_graphics.py` из G2AI_ME.

### 3. Единственная настоящая, ранее не обсуждавшаяся ниша — Markdown-слой

Vector-native «де-рендеринг» чартов (реконструкция данных из векторных path'ов, не из
растра/OCR) — реальное prior art (ChartDetective, Mystique, svgdigitizer, figverify),
но каждая реализация либо полуавтоматическая (человек размечает оси в UI), либо
свежий исследовательский дроп без внедрения (figverify — 2 звезды, 3 коммита, июнь
2026). Ни одна не является maintained-инструментом уровня production, и даже лучшая
(figverify) даёт bit-exact результат только для matplotlib и деградирует до 3–4
значащих цифр в общем случае — это реконструкция через инверсию координат, не
lossless-чтение кэша, категориально другая операция, чем чтение `numCache`.

Отдельно нашёлся реальный, узкий и ранее не обсуждавшийся пробел на другом уровне:
**Docling и marker знают bbox+подпись фигуры внутри своей JSON-модели, но теряют это
в дефолтном Markdown-выводе** — фигура превращается в голый `<!-- image -->` без
позиции/подписи (Docling
[#2376](https://github.com/docling-project/docling/issues/2376),
[discussion #1146](https://github.com/docling-project/docling/discussions/1146);
marker [#838](https://github.com/datalab-to/marker/issues/838)). MarkItDown вообще не
имеет позиционной модели (открытый feature request
[#94](https://github.com/microsoft/markitdown/issues/94)). Единственный, у кого есть
явная гарантия для составных инфографик («shared captions yield grouped subfigures
with individual bboxes») — Reducto, но только в закрытом JSON API, не в тексте
Markdown.

Это концептуально то же самое, что уже делает refigure для DOCX-композитных фигур —
positioned zero-loss маркер прямо в Markdown-потоке. Такой гарантии на уровне самого
Markdown-текста сегодня нет ни у одного из проверенных PDF-инструментов.

Критичная оговорка: у DOCX эта техника работает, потому что группы объектов уже
детерминированно размечены в XML — refigure их просто читает. У PDF такой разметки
нет: чтобы найти границы фигуры, нужна ML-модель детекции layout (то, чем реально
пользуются Docling/MinerU внутри). Это другой технический фундамент, а не «пара дней
работы» — и он прямо противоречит принципу «no rasterize/OCR/VLM», на котором стоит
вся текущая позиция refigure.

## Как это меняет вердикт от 2026-08-04

Не меняет решение (PDF вне v1 scope), но уточняет и усиливает его с новой стороны:
самая очевидная гипотеза «перенести наш chart-engine на PDF» закрыта не как
«рынок переполнен» (аргумент 2026-08-04), а как **структурно невозможная** — свойство
формата, не вопрос усилий. «Крепкий середнячок» тоже не закрывает найденный реальный
пробел (семантическое качество чартов) — туда даже у лучшего игрока (Reducto) ушли
серьёзные ресурсы с неполным результатом.

## Открытый флаг для v2+ (не решение, не задача на сейчас)

Positioned zero-loss маркеры для PDF-фигур на уровне Markdown-вывода — узкая, реальная
и никем не закрытая ниша, концептуально родственная сильной стороне refigure. Требует
нового фундамента (ML layout-detection для обнаружения границ фигуры), которого у
refigure сегодня нет ни для одного формата — не «бесплатное расширение», отдельная
исследовательская задача, если/когда PDF когда-либо будет пересмотрен.
